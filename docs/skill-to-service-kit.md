# `skill-to-service` 메타스킬 — 운영진이 기대하는 결선 진행 방식

> 출처: 결선 교육 자료 `결선교육_최종.zip` → `[실습2-메타스킬] skill-to-service.zip` → `SKILL.md` (11,886 B).
> 노션 결선 가이드 「퀵 링크 모음」 첨부. 취득 2026-09-10 (브라우저 직접 다운로드 — API 경로는 HTTP 400).
> ⚠ 이 문서는 **공식 배포 자료의 요약**이다. 우리 판단·설계가 아니다. 원문은 스크래치패드 사본과 노션 첨부에 있다.

## 왜 중요한가

운영진이 "스킬을 서비스로 바꾸는 표준 절차"를 스킬 형태로 배포했다. **심사자가 기대하는 산출물의 모양이 여기 적혀 있다.**
zip 안의 다른 실습 자료(`[실습2-스킬] 계약서-위험-조항-검토기`)는 이 메타스킬의 시연 대상이다.

## 0. 「서비스」의 공식 정의

> 타임리 안이 아니라 **Vercel에 배포되어 계정 없이 URL로 누구나 쓰는 웹 서비스**. 사용자는 **비밀(키)을 하나도 넣지 않는다.**

- 나만의 스킬 = 내 계정, 내 설정, 생략이 많음
- 모두의 서비스 = 처음 보는 사람도 쓸 수 있음

## 1. 기대 아키텍처 (C-2 3항)

```
index.html  +  api/*.js   ← Vercel 서버리스
```

- **클라이언트는 같은 도메인 `/api`만 fetch.** 키·프록시 주소는 클라이언트 소스에 0
- 예선 스킬의 데이터 경로를 **`/api` 서버리스 함수가 그대로 이식**한다 (PRD 6항)
- 사용자 프로필은 **localStorage** (재방문 시 다시 묻지 않음, 초기화 버튼 제공)
- 환경변수는 Vercel `plain` / production+preview / upsert

**규모 감각**: HTML/JS는 **파일당 원문 3KB 이내 권장**. 커지면 파일을 나눈다. 즉 운영진이 상정한 MVP는 작다.

## 2. 3단계 모드 (A → B → C)

| 모드 | 트리거 | 하는 일 |
| --- | --- | --- |
| **A 대화** | "스킬을 서비스로 만들고 싶다" | 스킬 건강검진 → 「서비스를 위한 5 걸음」 |
| **B PRD** | "PRD로 정리해줘" | 대화를 11항목 미니 PRD로 압축 |
| **C 구현 가드** | "구현해줘" | 계획 → **승인** → 구현 → 배포 → 동작 확인 |

### A-0. 스킬 건강검진 (대화 시작 시 필수)

스킬을 **실제로 호출해서** '재료 명세서'를 표로 만든다:
입력과 반환(실제 응답 예시 1개) / 반환하지 못하는 것(범위 밖 질의를 일부러 1회 시도) / 실패 방식(오류 형태·응답 속도) / 필요한 설정(값은 출력 금지) / **이 스킬만으로 할 수 없는 일 3가지**

### A-1. 서비스를 위한 5 걸음

| 걸음 | 공식 질문 |
| --- | --- |
| ① **WHO** | "이 정보가 '있으면 편한' 사람 말고 **'없으면 곤란한' 사람**은 누구인가요?" |
| ② **WHEN** | "그 사람이 이 서비스를 **찾는 순간**은 언제인가요?" (시각·요일·사건 중 하나로) |
| — 차별화 | *"이 스킬을 왜 만들었나요? 주변에 실제로 필요로 하는 사람이 있나요?"* (②③ 사이 1회) |
| ③ **INPUT/OUTPUT** | "처음 온 사람이 화면에서 무엇을 입력하고, 그 대가로 무엇을 받으면 만족할까요?" |
| ④ **SETUP** | 실행 설정값(키·MCP 등) |
| ⑤ **SOLVE** | 서비스 정의 한 문장 |

WHO는 접근성·언어·비용·디지털 문해력 중 어디에 닿는지 한 번은 묻는다.
WHEN은 "웹은 언제든 URL로 온다"가 기본이므로, 서비스가 먼저 가야 한다면 공유 링크·알림 중 무엇인지 묻는다.

### B. 미니 PRD 11항목 (번호 그대로)

1) 한 줄 정의 (누구를 위해 무엇을) 2) 타깃 사용자(구체적 한 사람) 3) 문제 4) 트리거
5) **핵심 기능 — P0 최대 4개 + 나머지 전부 P1** 6) **스킬 매핑(예선 스킬 1개 이상 필수)**
7) 입력·출력 8) 필요 설정(표 3개: 배포 연결 / 서비스 키(이름·용도·발급처만, **값 금지**) / 사용자 프로필)
9) 데이터 규칙(출처·기준 시각, 없는 값은 '확인 불가', 추정 금지, 키는 서버에만, 최소 권한)
10) **성공 기준 — 시크릿 창 테스트 필수** 11) 제외 범위

PRD 뒤에 「걸음 ①~⑤ → PRD 항목 번호」 대응표를 붙이고, 빈 걸음은 "미해소"로 표시한다.
분량은 **10분 스케치 수준으로 짧게**. (제출 규격도 2쪽 내외 — `docs/finals-guide.md` §3)

### C. 구현 가드

- PRD 없으면 구현 안 함
- **계획 제시 후 그 턴을 끝내고**, 사용자가 **별도 턴에서 '승인'**이라고 말해야 구현 시작. "구현해줘"는 승인이 아님
- 순서: 사전점검(Vercel 커넥터) → **예선 스킬 실제 호출로 데이터 검증** → `index.html`+`api/*.js` → 환경변수 → 배포 → 실패 항목은 '확인 불가'로 남기고 **전체 실패 금지**

## 3. ⚠ Vercel 배포 함정 (원문 "어기면 실패한 실측 사례 있음")

- `VERCEL_CREATE_NEW_DEPLOYMENT`의 `files[].data`에 **파일 원문 텍스트 그대로**. **base64 금지** — base64 문자열이 그대로 서빙된 실패 사례
- 파일 내용을 **터미널 출력에서 복사하지 말 것** — 잘린 실패 사례. args에 직접 작성하고, 워크스페이스에도 같은 내용으로 저장
- **매 배포는 전체 파일 세트를 다시 올린다.** 일부만 올리면 기존 파일이 사라진다
- 공개 URL은 배포 해시 URL이 아니라 **프로젝트 프로덕션 도메인(`프로젝트명.vercel.app`)**. 해시 URL이 302 나는 건 정상

## 4. 완료 보고에 반드시 붙이는 4가지 (C-4)

① 스킬 호출 내역(스킬명·호출 횟수·결과)
② P0 요구사항별 충족 여부 체크리스트 표
③ 배포 후 검증(공개 URL, index·`/api` 상태 코드, **클라이언트 소스에 키·프록시 주소 0**)
④ 시크릿 창 테스트 안내(저장값 없는 첫 방문에서 무엇이 보이는지)

**금지**: P0 5개 이상 / 승인 턴 없이 구현 / 없는 데이터 추정 / 배포 해시 URL을 공개 URL로 보고 / 키·프록시 주소를 클라이언트 소스나 응답 JSON에 넣기

## 5. 우리에게 주는 함의 (사실 기록용, 판단 아님)

- 심사 「예선 스킬 활용도 30점」의 기계적 근거는 **PRD 6항 스킬 매핑**과 **C-4 ① 스킬 호출 내역**이다
- 「사용성 15점」의 기계적 근거는 **C-4 ④ 시크릿 창 테스트**다 — 제출 체크리스트에도 같은 항목이 있다
- P0가 최대 4개로 제한되므로, 기능 범위 논의(1차 멘토링 2번 질문)는 **P0 4개를 무엇으로 할 것인가**로 수렴한다
