## 1. 문제 (P-A 바퀴 재발명)

새 작업을 시작할 때, 같은 문제를 이미 겪고 해결한 기록(오픈소스·도구·에셋·사례·기술 블로그)이 밖에 있는데도 그걸 먼저 찾지 않거나 못 찾아서, 남이 이미 치른 시행착오를 처음부터 반복한다.

- 본인 근거: 이 문제 때문에 toolshelf 를 직접 만들어 "새 도메인 작업 전 먼저 조회"를 전역 규약으로 박아 둘 정도였다.
- 가치 축(사용자 확정): "안 풀린 문제를 판정해 준다"가 아니라 **"시행착오를 줄여 바퀴 재발명의 수고를 덜어 준다."**

## 2. 스킬이 하는 일 (한 흐름)

**받는 것**: 하려는 일 또는 막힌 문제 서술 한 문단 (예: "타워디펜스 게임을 만들려고 한다")

**하는 일**: ① 서술을 검색 가능한 질의로 번역 → ② `web_search` 로 기존 바퀴 수집(오픈소스·도구·에셋 사이트·사례, 출처 URL 필수) → ③ 작업 흐름 단계로 배치 → ④ 단계별로 "이미 있는 것 / 직접 해야 하는 것" 가름

**내는 것 (3종 세트)**:
| 산출 | 내용 |
| --- | --- |
| 채팅 요약 | 헤드라인 "N단계 중 M단계는 바퀴가 이미 있음" + 단계·바퀴 축약표 + 파일 안내. 파일이 안 열려도 이것만으로 완결 |
| `연구노트.md` | 단계·바퀴·요약·출처 URL·판단 근거 전체 기록. 같은 대화에서 다음 작업의 컨텍스트로 이어 씀 |
| `설계도.html` | 흐름 지도 (아래 §3). `assets/` 템플릿에 데이터만 주입해 생성 |

**범위 밖 (「언제 사용하지 않음」 후보)**: 계획 수립·일정 관리(플랜은 사용자 몫) / 이미 답을 아는 문제 / 취향·선호 문제 / 실행 대행.

## 3. 설계도.html 스펙 (흐름 지도)

- **좌→우 고정 스파인**: 단계 카드(예: 1 PRD·TRD 확정 → 2 에셋 수집 → … → 결과물 판정)가 메인 연결선으로 이어짐. 위치 고정 = 이야기 순서 보존.
- **바퀴 노드**: 각 단계 카드 주위에 스프링 물리로 매달림(미세 부유, 드래그 시 출렁, 놓으면 복귀). 노드 옆 요약 한 줄 상시 표시, 호버/클릭 → 팝오버(설명 + 출처 링크).
- **인터랙션 필수**: 휠 줌 인/아웃 · 좌클릭 그랩 팬. SVG viewBox 변환.
- **연출**: 로드 시 스파인 좌→우 드로잉, 카드 페이드인, 호버 하이라이트 (CSS 트랜지션).
- **제약**: 전부 바닐라 JS/CSS 인라인. 외부 라이브러리·CDN·폰트 0 (three.js 기각 사유: CDN 의존=실격 리스크).
- **구현 방식**: 완성 템플릿을 스킬 `assets/설계도-템플릿.html` 에 두고, 실행 시 데이터(단계·노드·요약·출처)만 채운다. 매 실행 통짜 생성 금지.

### finding (7d 1차)

- **F-1 · 트리거 문장으로 스킬이 안 걸린다.** `/pathfind` 로만 발화한다. **[등급 하향 2026-08-22]** 처음엔 재현 가능성 20점 직격으로 봤으나 **과대평가였다.** 공식 FAQ 가 "평가 시 `/스킬명` 명령어로 **강제 실행**하여 점검"이라고 명시한다(`research/2026-08-20-m1-ot-notes.md` §52). 심사 실행 경로는 명시 호출이고 그것은 완주한다. 같은 FAQ 가 트리거 문장 테스트를 **권장**하므로 F-1 은 **실격 리스크가 아니라 권장 사항 미달**이다.
  - **1차 수정 시도 실패 (2026-08-22)**: description + 「언제 사용」에 사용자 발화 예시 4종을 넣고 재커밋했으나 **동일 문장으로 재검증 시 여전히 미발화**. 일반 채팅 답변만 나왔다(다만 답변이 "연구노트 형태로 정리해드릴게요"라는 스킬 어휘를 빌려 쓴 것으로 보아 description 은 컨텍스트에 들어가되 실행으로 이어지지 않는다). **추가 추측 수정 중단** — 플랫폼의 자동 호출 자체가 약할 가능성이 있다(같은 계정의 `tone-softener` 도 같은 조건). 여유 구간(8/28~30)에 재시도한다.
- **F-2 · 조사 전에 되묻고 멈춘다.** `/pathfind` 직후 단계 분해까지만 하고 "지금 바로 조사할까요, 아니면 3개 먼저 정할까요?"로 정지했다. 설계상 「입력이 모호하면 되묻기」가 있으나, 심사자는 보통 한 턴만 돌려 본다. **되묻더라도 기본값으로 조사를 진행하고 나중에 조정받는 형태**가 안전하다.

- **[플랫폼 함정] `/스킬명 내용` 을 한 줄로 치면 스킬이 안 붙을 때가 있다.** 확실한 호출은 `/스킬명` → Enter(칩 생성) → 내용 입력 → Enter. 1차 무관 입력 테스트가 이것 때문에 무효였다(스킬 미로딩). **폼 ③번에 호출 방법을 명확히 적어야 한다.**

## 9. 7b · 설계도 템플릿 (진행 중, 2026-08-22)

### 접근 변경
어제(8/21) 실패는 통짜 템플릿을 만들고 디버깅한 것이었다. 이번엔 **줌·팬만 되는 최소 재현본부터** 세우고 확정 후 스파인·노드를 얹는 순서로 바꿨다.

### 원인 진단 (Solar, 대화 중 도출)
`viewport` 요소에 `transform: scale()` 을 걸면 브라우저가 보는 "보이는 영역"과 transform 이 닿는 좌표계가 어긋난다. 이미 scale 이 적용된 요소의 bounding box 기준으로 이벤트 좌표를 계산하면 화면 밖 밀려남이 생긴다.

**채택한 해법**
- `transform` 을 **하나로 유지**: `translate(tx,ty) scale(s)` — scale 과 translate 를 따로 걸지 않는다
- 줌 기준점 = 휠 이벤트 순간의 **커서 위치**
- 드래그는 `tx,ty` 만 가감, scale 과 섞지 않는다
- 좌표 계산은 **화면 픽셀 기준**(`clientX/clientY` + `getBoundingClientRect`)이며 transform 이 적용된 요소의 bounding box 에 종속시키지 않는다

### 7b 진행 — 스파인 + 단계 카드 (`steps-flow.html`)

### ② 문제 정의 — *채점: 문제정의 및 실용성 · 독창성*

무언가를 새로 만들려는 사람이 **작업을 시작할 때마다** 겪는 문제입니다.

타워디펜스 게임을 만들어 보자고 마음먹으면, 이미 누군가 만들어 둔 오픈소스도 있고 무료 에셋도 있고 같은 걸 만들어 본 사람의 기술 블로그도 있습니다. 그런데 그걸 먼저 찾지 않고 그냥 처음부터 시작합니다. 한참 만들다가 뒤늦게 "아 이거 이미 있었네"를 발견합니다.

검색을 아예 안 하는 게 아닙니다. **뭘 검색해야 할지를 모르는 것**이 진짜 문제입니다. 하려는 일이 어떤 단계로 이루어지는지 아직 모르는 상태라, 검색어 자체를 못 만들고 대충 찾다 맙니다. 그래서 남이 이미 치른 시행착오를 처음부터 다시 치릅니다.

- **누가**: 무언가를 새로 만들거나 해내려는 사람 (개발자·기획자·1인 제작자)
- **언제**: 새 작업에 착수하는 시점마다
- **어떤 작업에**: 선례 조사 — 오픈소스·무료 에셋·튜토리얼·유사 사례를 훑어 "이미 있는 것"을 파악하는 일
- **왜 반복되나**: 이미 있는 것을 찾으려면 "내가 하려는 일이 어떤 조각들로 이루어지는가"를 먼저 알아야 하는데, 새 작업일수록 그 조각을 모릅니다. 그래서 검색이 겉돌고, 결국 처음부터 직접 만드는 쪽으로 기웁니다
- **소요**: 착수 전 선례 조사에 반나절 안팎이 들고, 그마저 건너뛰면 이미 있던 오픈소스나 에셋을 뒤늦게 발견해 며칠치 작업을 통째로 버립니다. 잃는 것은 시간만이 아닙니다. 남이 이미 겪고 해결해 둔 시행착오를 처음부터 다시 겪습니다

저는 이 문제 때문에 쓸 만한 도구를 모아 두는 개인 도구 목록을 따로 만들고, "새 도메인 작업을 시작하기 전에 먼저 조회한다"를 스스로의 작업 규칙으로 박아 둘 정도였습니다. 규칙으로 강제해야 할 만큼 자주, 그리고 잊어버리기 쉬운 일이었습니다.

### ③ 문제 해결 방식 — *채점: 실용성 · 독창성*

**단계를 먼저 나누고, 그 단계를 검색어로 씁니다.** 이 순서가 핵심입니다.

1. 하려는 일을 일하는 순서대로 단계로 분해합니다(주제에 따라 4~7개). 이 분해가 곧 검색의 뼈대가 됩니다
2. 단계마다 오픈소스 · 무료 에셋 · 기술 블로그/튜토리얼 · 참고 사례를 훑어 실제 웹 검색으로 자료를 모읍니다
3. 찾은 것마다 **"가져다 써도 됨 / 섞어야 함 / 직접 해야 함"을 근거와 함께 갈라** 붙입니다
4. 결과를 채팅 요약 + 연구노트 파일 + 흐름 지도, 세 가지로 냅니다

**기존 스킬과의 차이.** 스토어를 `리서치`·`research`·`조사`·`사례` 키워드와 시맨틱 검색으로 훑었습니다. 가장 가까운 것은 `tech-trend-research`(키워드를 받아 최근 트렌드를 3줄 요약과 표로 정리)였습니다. 그 스킬은 **키워드의 최신 동향을 요약**하고, `pathfind`는 **하려는 작업에 대해 기존 해법이 있는지 판정하고 작업 흐름 위에 배치**합니다. 대상도 다르고(키워드 vs 작업) 산출도 다릅니다(동향 요약 vs 단계별 가름).

**가치의 축은 "판정"이 아니라 "시행착오 절감"입니다.** 이 스킬이 "그건 이미 풀렸다"고 알려 주는 것 자체가 목적이 아니라, 남이 이미 치른 시행착오를 다시 치르지 않게 하는 것이 목적입니다. 그래서 선례가 없을 때도 유용합니다. "선례 없음"은 "안심하고 직접 만들어도 된다"는 판단이기 때문입니다.

> **참고 출처**: 공개 스킬의 코드나 지침을 가져다 쓰지 않았습니다. 스토어 조사는 차별점 확인 목적의 열람이며, 위에 언급한 `tech-trend-research`(타임리 에이전트 스토어)가 비교 대상으로 확인한 유일한 인접 스킬입니다. 조사 결과에 포함되는 외부 링크는 모두 실행 시점의 웹 검색 결과에서 나온 것이며 스킬이 URL을 생성하지 않습니다.

### ④ 스킬 동작 방식 — *채점: 재현 가능성 · 설계 체계성*

**입력**: 하려는 일 또는 막힌 문제를 한 문단으로. (예: "개인 가계부 데이터를 분석해서 월별 소비 리포트를 자동으로 만들어 주는 도구를 하나 만들어보려고 해")

**처리**

1. **대상 판정을 첫 줄에 출력합니다.** "만들거나 해내려는 대상"과 "뭐부터/이미 있는지"가 함께 있으면 대상입니다
2. 하려는 일을 단계로 나눕니다(주제에 따라 4~7개). 단계는 검색 채널이 아니라 **일하는 순서**여야 합니다
3. 단계마다 웹 검색으로 자료를 모으고, 각 단계에 **핵심 문장 2~3개 · 판단과 그 근거 · 할 일 2~3개(순서 · 무엇을 · 왜)** 를 채웁니다
4. 채운 내용을 JSON으로 만들어 **스킬에 들어 있는 파이썬 스크립트에 넘깁니다.** 스크립트가 구조를 검사해 통과한 것만 파일로 씁니다

**출력** (3종)

- **채팅 요약** — 단계 구성 + 단계별 판단 + 핵심 참고 링크 + 이번 조사에서 가정한 것. 파일을 안 열어도 이것만으로 완결됩니다
- **`research-note-<주제>.md`** — 단계별 근거와 출처 URL 전문 기록
- **`flow-<주제>.html`** — 왼쪽에서 오른쪽으로 흐르는 단계 카드 지도. 카드에는 훑을 문장만 불릿으로 얹고, 자세한 설명과 판단 근거 · 할 일 · 출처는 카드를 눌러 여는 창에 담습니다. 찾은 자료는 카드 위아래에 점으로 매달리고(좌우는 이웃 카드 자리라 비워 둡니다), 점을 누르면 근거와 출처가 열립니다. 휠 확대축소와 드래그 이동이 되고, 처음 열 때 라벨까지 포함해 전체가 화면에 맞게 들어옵니다

**설계 근거 — 세 가지 원칙을 실측으로 세웠습니다.**

**(1) 지시는 "금지"가 아니라 "산출"로 씁니다.**
`SKILL.md`에 "이런 입력은 받지 마라", "템플릿을 무시하고 새로 짜지 마라"처럼 **금지형으로 쓴 지시는 반복 수정에도 지켜지지 않았습니다**(하루에 같은 원인으로 3회 실패). 같은 규칙을 **"첫 줄에 판정을 써서 내놓아라", "템플릿을 읽고 바꾼 범위를 한 줄로 내놓아라"처럼 산출형으로 바꾸자 한 번에 지켜졌습니다.**

**(2) 그런데 산출형 지시도 응답 형식까지가 한계입니다. 도구 호출은 글로 강제할 수 없습니다.**
"파일을 썼다는 것을 출력하라"고 지시하면 파일을 안 쓰고 문장만 만들어 냅니다(3회 시도 전부 실패). 그래서 **파일 쓰기를 파이썬 스크립트로 빼내고, 그 스크립트가 출력한 값(저장 경로와 바이트 수)을 응답에 옮겨 적게 했습니다.** 도구를 실제로 부르지 않으면 만들어 낼 수 없는 값이라, 이 값이 응답에 있다는 것 자체가 파일이 생겼다는 증거가 됩니다.

**(3) 구조는 스크립트가, 내용의 폭은 지시가 담당합니다.**
글로 된 지시만으로는 "단계 × 조사 채널"이라는 두 층이 한 층으로 무너졌습니다. 단계 제목이 "오픈소스 찾기 / 에셋 찾기"처럼 검색 채널로 변해 버렸습니다. **층을 지키는 일은 스크립트의 구조 검사로 옮기고**(채널 명사가 제목에 들어오면 거부), 조사 폭 같은 양적 지시만 글에 남겼습니다. 같은 입력 · 같은 모델인데 산출 구조가 세 번 달라졌고, 바뀐 것은 `SKILL.md` 한 문장과 스크립트 검사 규칙뿐이었습니다.

- 다만 **구조 검사가 정상 입력을 막는 쪽이 훨씬 비쌉니다.** 잘못 막으면 스킬이 완주를 못 합니다. 그래서 검사 규칙은 좁게 잡고, **오류 메시지가 예로 드는 값이 그 검사를 반드시 통과하는지 스크립트가 스스로 점검**하게 했습니다.

### 대제목 버그 확정 (2026-08-23) — `firstChild` 대입은 no-op

사용자 승인 후 `pathfind-example-2.html` (34,995 bytes) 을 내려받아 정적 검사했다. **관측 아티팩트가 아니라 실제 코드 버그였다.**

```js
// boot() 안
if (eyebrow) {
  eyebrow.firstChild = document.createTextNode('안드로이드 투두 앱 구현 흐름도');
}
```

`Node.firstChild` 는 **읽기 전용 속성**이라 이 대입은 아무 일도 하지 않고 예외도 던지지 않는다. 그래서 대제목이 영원히 빈 상태였다. 템플릿 사용 안내 문구도 `eyebrow.firstChild.data = ...` 로 적혀 있어 같은 문제를 재생산할 참이었다(빈 요소면 `firstChild` 가 `null` 이라 그쪽은 오히려 예외를 던진다).

**수정**: `eyebrow.textContent = '<작업명>'`.

### 미결 설계 질문 (2026-08-24)

**Q1. 카드·엣지를 드래그 가능하게 하면 겹침이 사라지나?**

**Q3. 계획→설계→구현→검증→배포 대단계 + 세부는 모달, 이 구조가 가능한가?**

**구조적 사실 — 서비스화 설계를 좌우한다**

- **`pathfind` 는 웹 검색을 내장하지 않는다.** 호출자(에이전트)가 단계별 검색을 수행해 `findings` 로 채워 넣는다.
  실제 데이터·URL·검색 결과는 전부 호출자 책임. 스킬 본체는 **스키마 검증 + 템플릿 렌더러**다.
  → 웹 서비스로 옮기면 **`/api` 가 검색을 대행**해야 한다. 스킬을 그대로 이식하는 것이 아니다.
- 입력: JSON 객체(`topic`, `out_md`, `out_html`, `search_calls`, `steps[]`)

- 실패 방식: 스키마 검증 실패 시 **stderr ERROR + exit 2**. 템플릿 파일 부재·경로 밖 출력도 실패
- 필요 설정: `assets/steps-flow-template.html`, `assets/lucide-icons.json` 만. **외부 키·환경변수 불필요**, 표준 라이브러리만 사용
