# pathfind

## 먼저 할 일: 응답 첫 줄에 판정을 쓴다 (가장 중요)

이 스킬은 **어떤 입력이 들어와도 응답의 맨 첫 줄에 판정 문장을 쓰는 것**으로 시작한다. 이 판정 문장은 선택 사항이 아니라 출력물의 일부다. 그 뒤의 모든 행동은 이 판정 결과에 따라 결정된다.

판정 문장은 다음 두 가지 중 하나여야 한다.

**A. 대상 맞음 (이어서 진행)**

> "판정: 이 입력은 pathfind 대상이다. 만들려는 대상(타워디펜스 웹 게임 등) + 뭐부터/이미 있는지/비슷한 게 있는지에 대한 질문이기 때문이다."

이 판정을 첫 줄에 썼으면, 그 아래부터는 아래 "실제로 할 일"대로 이어서 진행한다. 단계 분해 → 4개 채널 조사 → 판단 → 채팅 요약 + 연구노트 파일.

**B. 대상 아님 (여기서 끝)**

> "판정: 이 입력은 pathfind 대상이 아니다. 이유는 …"

이 판정을 첫 줄에 썼으면, **응답에 넣을 것은 아래 두 줄뿐이다.** 그 두 줄만 써서 응답을 끝낸다.

1. 이 스킬이 무슨 용도인지 한 줄
2. 입력을 스킬 용도로 바꾸고 싶으면 어떻게 말하면 하는지 짧게 한 줄 (선택)

그 두 줄만 내놓은 뒤에는 여기서 멈춘다. 판정 B가 나온 경우에는 조사·연구노트·파일 작성·상담·조언·긴 설명을 더 이어 쓰지 말고, 위 두 줄로만 응답을 끝낸 상태로 내놓는다.

예:

> 판정: 이 입력은 pathfind 대상이 아니다. 친구와의 관계에서 먼저 연락할지 말지 고민하는 내용이라, 만들려는 대상 + 뭐부터/이미 있는지 질문이 아니기 때문이다.
>
> pathfind는 무언가를 새로 만들거나 해내려는 일을 앞두고, 이미 세상에 나와 있는 것(오픈소스·무료 에셋·튜토리얼·참고 사례)을 단계별로 찾아서 "가져다 써도 됨" vs "직접 해야 함"으로 갈라주는 스킬이다.
>
> 만약 "XXX를 만들어보려는데 뭐부터 찾아봐야 할지 모르겠다"처럼 만들려는 대상이 있으면 그때 다시 걸 수 있다.

## 판정 기준 (무엇을 대상이라고 보는가)

pathfind 대상으로 보는 입력은 아래 조건을 만족한다.

- **만들려는 대상, 해내려는 일이 명시돼 있다** (게임, 서비스, 앱, 영상, 문서, 도구, 제작할 무언가 등)
- **그걸 만드는 과정에서 "뭐부터 찾아봐야 할지", "이미 비슷한 게 있는지", "무료로 쓸 수 있는 코드/에셋이 있는지", "비슷한 사례가 뭔지"를 알고 싶어 한다**

즉, 핵심 신호는 **만들 대상 + "뭐부터/이미 있는지/비슷한 게 있는지"** 가 함께 나오는 것이다.

### 대상으로 보는 예시

- "타워디펜스 웹 게임을 하나 만들어보자 — 타워 4~5종, 적은 웨이브 단위, 맵은 타일 기반"
- "개인용 노션 대체 서비스를 만들어보려는데, 어디서부터 손을 대야 할지, 비슷한 오픈소스가 있는지 모르겠다"
- "2D 플랫폼 게임을 만들고 싶은데, 무료 타일 에셋이나 비슷한 구현체 튜토리얼이 있는지 먼저 찾아보고 싶다"

### 대상으로 보지 않는 것 (판정 B로 간다)

아래 중 하나라도 핵심이면 대상이 아니다. 만들려는 대상이 없거나, 목적이 조사·분석이 아니라 다른 데 있기 때문이다.

- **인간관계·감정 상담**: 친구/연인/가족/동료와의 갈등, 사과·연락 여부, 마음 정리, 위로, 관계 조언 등
  - 예: "친구랑 싸웠는데 먼저 연락할까요", "헤어져야 할지 모르겠어요", "상사가 자꾸 짜증나요"
- **취향·고르기**: 영화/음악/책/맛집/선물/여행지/디자인 취향 등을 대신 골라달라는 요청
  - 예: "이번 주말에 볼 영화 추천해줘", "선물 뭐 사야 좋을까요"
- **이미 답을 알고 있는 일 / 확인 질문**: 본인이 이미 정한 선택을 그냥 동의받거나, 검색 한 번이면 끝나는 단순 사실 확인
  - 예: "이 얘기 맞죠?", "이거 맞나 확인만 해주세요" (사실 확인이 목적이면 일반 서치가 맞다)
- **대신 실행해달라는 일**: "이 파일 정리해줘", "이 메일 대신 보내줘", "이 코드 대신 짜줘"처럼 조사·분석이 아니라 실행이 목적인 요청
- **그냥 의견·조언 구하기 (만드는 일과 무관)**: "평범하게 어떻게 생각하세요", "제가 잘 하고 있는 걸까요" 같은 일반 상담·인생 조언
- **문장에 만들려는 대상이 전혀 없는 말**: "갑자기 이런 생각이 드는데…", "요즘 마음이…", "어떻게 살아야 할지 모르겠어요" 등

### 애매한 경우

- **빈 입력, 대상이 안 보이는 경우**: 스킬 용도 자체는 맞지만 대상이 빠졌다. 이때는 판정 B로 보내되, "만들려는 대상이 안 보인다"고 말하고 예시를 주며 되묻는다. "걸러야 하는 입력"과 이 경우를 헷갈리지 않는다 — 빈 입력은 금지 대상이 아니라 정보가 부족한 경우다.
- **대상이 보이지만 디테일이 짧은 경우 (새 규칙)**: 만들 대상이 명시돼 있으면 정보가 다소 부족해도 되묻고 멈추지 않는다. 스킬은 아래의 기본값과 추정을 스스로 정해 한 턴에 끝까지 진행하고, 무엇을 어떻게 가정했는지는 마지막 조정 안내 절에 적는다. 사용자가 그 가정을 보고 고치라고 하면 그때 조정한다.
- 각 단계 안에서는 오픈소스·무료 에셋·튜토리얼·블로그·참고 사례 네 종류를 findings로 찾는다. 단계마다 웹 검색을 실제로 호출해 그 결과를 findings로 옮긴다. 단계 제목에는 채널을 넣지 않고 그 단계에서 실제로 하는 일(설계, 구현, 검증, 배포 등)로만 적는다.
- **모든 단계에 tasks를 2~3개 채워서 내놓는다.** tasks는 선택 필드지만, 이 스킬에서는 계획서 수준으로 단계당 작업 2~3개를 반드시 적는다. 각 task는 (1) 순서, (2) 그 단계에서 실제로 하는 작업 한 줄, (3) 왜 하는지 한 줄로 구성한다.
- **각 단계의 desc는 그 단계에서 하는 일의 핵심 문장 2~3개로 쓴다.** 각 문장은 짧고 독립적으로, 다른 문장에 기대지 않게 쓴다. 템플릿은 desc를 문장 단위(마침표 '다.' 기준)로 잘라 각 문장 앞에 · 을 붙인 목록으로 표시하며, 문장이 하나면 불릿 없이 그대로 보여준다.

## 응답을 시작하기 전에 끝내는 동작 (대상 맞음 판정일 때만)

대상 맞음 판정(A)을 첫 줄에 썼으면, 조사를 다 끝낸 뒤 아래 동작을 **하나의 스크립트 실행으로 끝낸다.**

**핵심**: 파일 생성은 산문 지시로 시키지 않는다. 조사 결과를 정해진 JSON 스키마로 정리한 뒤, 그 JSON을 `scripts/render.py`의 stdin으로 넘겨 한 번 실행한다. 스크립트가 연구노트 마크다운 파일과 흐름도 HTML 파일을 둘 다 작성하고, stdout에 **검색 호출 횟수와 각 파일의 경로(`./...` 형태)와 바이트 크기**를 찍는다.

에이전트가 할 일은 다음 한 가지다.

1. 조사를 마친 뒤, 아래 "조사 결과 JSON 스키마"대로 조사 결과를 JSON 객체로 만든다.
2. 그 JSON을 stdin으로 `scripts/render.py`를 실행한다. 실행 명령은 아래 "스크립트 실행 방법"을 그대로 쓴다.
3. 스크립트 실행이 끝나면(stdout에 경로+바이트가 찍히면), **그 stdout에 찍힌 내용과 바이트 값을 그대로 응답의 '저장 결과' 섹션에 옮겨 적는다.**

이 한 번의 스크립트 실행으로 연구노트 + 흐름도 설계도 두 파일이 모두 만들어진다. 에이전트 응답 본문에는 파일 쓰기 절차, 템플릿 교체 절차, 마크다운/HTML 작성 절차를 적지 않는다.

### 조사 절차 (한 단계에 한 번 웹 검색)

- 각 단계마다 웹 검색 도구 호출을 **한 번만** 수행한다. 한 단계에 여러 검색을 돌려 응답을 늘리지 않는다.
- 검색은 그 단계의 조사 목적을 살리는 검색어(query) 하나로 수행한다.
- 각 findings 항목의 `query`는 그 발견을 찾을 때 실제로 넣은 검색어를 그대로 옮긴다.
- 각 findings 항목의 `evidence`는 검색 결과 텍스트에서 실제로 있었던 문장 한 개를 그대로 옮긴 것이다. 기억으로 지어내거나 요약·번역·의역하지 않는다.
- 검색 결과에서 확인되지 않은 URL은 findings에 넣지 않는다. **검색 결과에서 아무것도 못 찾은 단계는 findings를 빈 배열([])로 두고 verdict를 "선례를 못 찾음"으로 낸다. 이것도 정상 결과다 — "이건 정말 내가 만들어야 하는 바퀴"라는 판단이다.**
- 단계마다 검색을 수행하지 않은 상태에서 URL·evidence를 지어내지 않는다. url은 검색 결과에서 확인된 주소만 넣는다. 확인할 수 없는 자료는 findings에서 뺀다.

### 조사 결과 JSON 스키마 (고정)

조사의 최종 산출물은 아래 스키마를 정확히 따르는 JSON 객체 하나다. 에이전트는 조사 결과를 이 모양으로 정리한 뒤, 그 JSON을 stdin으로 스크립트에 넘긴다.

```
top-level:
  - topic: string — 입력 주제(예: "타워디펜스 웹 게임").
  - out_md: string — 연구노트 출력 파일명(예: `research-note-타워디펜스-웹.md`).
  - out_html: string — 흐름도 출력 파일명(예: `flow-타워디펜스-웹.html`).
  - search_calls: integer — 이번 조사에서 실제로 수행한 웹 검색 호출 횟수(필수). 최소 1 이상. 기억·추정으로 채우지 않는다.
  - steps: array (비어 있으면 안 됨)
    각 원소:
      - no: number 또는 string — 단계 번호/식별자
      - title: string — 단계 이름
      - desc: string — 핵심 문장 2~3개
      - icon: string — 선택. 아래 "아이콘 이름" 표 중 하나. 없거나 표에 없는 이름이면 기본 아이콘으로 그려진다.
      - verdict: string — 아래 허용값 중 정확히 하나
        - "가져다 써도 됨"
        - "직접 해야 함"
        - "섞어야 함"
        - "선례를 못 찾음"
      - verdictReason: string — 선택. 단계의 판정 근거를 한 줄로 적는다. 없으면 render.py·템플릿이 verdict만으로 표시한다.
      - tasks: array — 선택. 이 단계에서 할 작업을 순서대로 적는다. 없으면 템플릿 모달이 desc로 폴백한다.
          각 원소:
            - order: number — 작업 순서(1부터).
            - task: string — 할 일 한 줄.
            - why: string — 이 작업을 왜 하는지 한 줄.
      - findings: array
        각 원소:
          - kind: string — 아래 허용값 중 정확히 하나
            - "오픈소스"
            - "무료 에셋"
            - "튜토리얼·블로그"
            - "참고 사례"
          - name: string — 발견 항목 이름
          - query: string — 그 발견을 찾을 때 실제로 넣은 검색어(필수, 빈 문자열 금지)
          - evidence: string — 검색 결과 텍스트에서 그대로 옮긴 한 문장(필수, 빈 문자열 금지)
          - note: string — 한 줄 메모/판단 근거
          - url: string — 실제 확인된 URL(빈 문자열·누락 금지). URL이 없는 발견은 이 항목으로 넣지 말고 해당 발견 자체를 findings에서 제외한다.
```

각 단계에 icon 을 하나 고른다. 아래 "아이콘 이름" 표에서 그 단계의 성격에 가장 가까운 이름을 쓴다.

### 아이콘 이름 (steps[].icon)

| 단계 성격 | icon |
|---|---|
| 방향·범위 정하기, 기획 | `compass`, `target` |
| 설계, 화면·구조 잡기 | `pencil-ruler`, `layout-dashboard` |
| 코드 구현 | `code-xml` |
| 데이터·저장소 | `database` |
| 서버·API·인프라 | `server`, `cpu`, `wifi` |
| 모바일 앱 | `smartphone` |
| 게임 | `gamepad-2` |
| 디자인·그림·에셋 | `palette`, `image` |
| 영상·음성 | `video`, `film`, `mic`, `headphones` |
| 글쓰기·문서 | `pen-line`, `file-text`, `book-open` |
| 사람·운영·커뮤니티 | `users`, `message-square`, `bot` |
| 알림·일정 | `bell`, `calendar` |
| 결제·판매 | `credit-card`, `shopping-cart` |
| 지도·위치 | `map`, `globe` |
| 보안·개인정보 | `shield` |

**중요**

- verdict와 kind는 위에 적힌 문자열 그대로만 쓴다. 비슷한 말로 바꾸지 않는다.
- `query`와 `evidence`는 반드시 실제 웹 검색 결과에 있었던 것만 옮긴다. 두 필드 중 하나라도 비어 있으면 render.py가 exit 2로 막는다.
- url은 실제 확인된 것만 넣는다. url이 없는 발견은 findings에 넣지 않는다.
- 템플릿은 스크립트 내부에서 자동으로 읽는다. 에이전트가 템플릿을 직접 만지거나 HTML을 새로 짜지 않는다.

### 단계 분해

- 단계 수는 주제에 맞게 4~7개 사이에서 정한다. 작은 일은 4개, 큰 일은 7개까지.
- 단계 제목은 카드 한 줄에 들어가도록 한글 기준 24자 이내로 적는다.
- 단계 분해는 만드는 일을 실제로 하는 일 순서대로 나눈다. 예를 들어 "방향 정하기 → 설계 → 구현 → 검증 → 배포"처럼, 각 단계가 실제로는 손이 가는 작업 단위가 되도록 나눈다.

### 스크립트 실행 방법

조사 결과를 정리한 JSON을 `scripts/render.py`의 stdin으로 넘겨 실행한다. 실행 예는 아래 중 하나를 그대로 쓴다(작업공간 루트 기준).

```bash
python .pi/skills/pathfind/scripts/render.py <<'PYEOF'
{"topic": "...", "out_md": "research-note-....md", "out_html": "flow-....html", "search_calls": 5, "steps": [...]}
PYEOF
```

또는 파일로 먼저 썼다면:

```bash
python .pi/skills/pathfind/scripts/render.py < pathfind-input.json
```

스크립트는 표준 라이브러리만 쓰며, 외부 패키지 설치가 필요 없다.

스크립트가 성공하면 stdout에 아래 형태로 경로+바이트가 찍힌다.

```
연구노트: ./research-note-<주제>.md — <n>바이트
흐름도 설계도: ./flow-<주제>.html — <n>바이트
```

### 스크립트 출력 처리 (중요)

스크립트가 stdout에 찍은 **경로와 바이트 값을 그대로 응답의 '저장 결과' 섹션에 옮겨 적는다.** 바이트 값은 스크립트를 실제로 실행하지 않으면 만들 수 없는 값이므로, 실행하지 않았으면 이 값이 응답에 들어올 수 없다.

스크립트가 실패하면(stderr에 ERROR가 찍히고 exit code가 0이 아니면) 실패한 것이다. 이때는 JSON을 다시 확인해 오류를 고쳐 다시 실행한다. "작성 완료"라고만 쓰고 파일도 stdout도 없는 응답은 내지 않는다.

스크립트는 필수 키가 빠지거나 허용값이 틀리면 명확한 ERROR 메시지를 stderr에 내고 종료한다. 에이전트는 그 메시지를 보고 JSON을 고쳐 재실행한다.

### 응답에 넣을 섹션

응답 본문에는 아래 네 섹션만 넣는다. 파일 쓰기 절차나 조사 절차는 이 섹션에 넣지 않는다.

### 1. 판정 (첫 줄)

- "판정: 이 입력은 pathfind 대상이다. …" 또는 "판정: 이 입력은 pathfind 대상이 아니다. …"를 응답의 맨 첫 줄에 쓴다.

### 2. 저장 결과 (스크립트 stdout + 공유 카드)

스크립트 실행 후 stdout에 찍힌 내용을 그대로 옮긴다.

- 연구노트: `./research-note-<주제>.md` — <n>바이트
- 흐름도 설계도: `./flow-<주제>.html` — <n>바이트

스크립트로 두 파일을 만든 직후, `share_file`을 연구노트 md와 흐름도 html 각 파일에 대해 두 번 호출해 채팅에 카드로 올린다. 두 카드는 각각 눌러서 브라우저에서 바로 열 수 있다.

위 경로와 바이트는 스크립트 stdout에 실제로 찍힌 값이어야 한다. 스크립트 실행 없이 지어내지 않는다.

### 3. 채팅 요약

- 단계 목록(각 단계 한 줄 설명 포함)
- 단계마다 "가져다 써도 됨" / "직접 해야 함" / "섞어야 함" / "선례를 못 찾음" 판단 요약
- 핵심 링크 몇 개(상세 전체는 연구노트에서)
- 마지막 한 줄: "직접 해야 함"과 "선례를 못 찾음"인 단계가 어디인지 — 그게 이 작업에서 정말 새로 만들어야 하는 바퀴다.

### 4. 조정 안내 (한 번만)

- 이번 진행에서 스킬이 스스로 정한 기본값·가정 목록을 아래에 적는다.
  - 단계 수 (4~7개 중 실제 사용한 개수)
  - 단계 제목이 짧다고 보고 진행한 경우 그 가정
  - 조사한 채널 범위(오픈소스·무료 에셋·튜토리얼·참고 사례)
  - 조사 깊이(단계마다 1회 검색)
  - 정보가 부족할 때 채운 추정
- 사용자는 이 목록을 보고 "이건 이렇게 고쳐줘"를 말하면 된다. 그때 그 부분만 조정해서 다시 진행한다.

## 매 실행에서 반드시 할 일 (대상 맞음 판정일 때만)

- 매 실행에서 **각 단계마다 웹 검색 매 호출을 실제로 수행한다.** 위 조사 절차대로, 단계마다 한 번씩 웹 검색을 호출하고 그 결과를 findings에 옮긴다.
- 조사가 끝나면 **render.py를 한 번 실행한다.** 스크립트 실행으로 연구노트 마크다운과 흐름도 HTML 두 파일을 생성한다.
- 그 다음 **share_file로 파일 두 개를 채팅에 올린다.** 올릴 대상은 이번 실행에서 만든 연구노트 md와 흐름도 html 두 파일뿐이다. 이전 실행 파일이나 다른 파일을 올리지 않는다.
- 스크립트가 stdout에 찍은 **경로와 바이트를 응답에 옮겨 적는다.** 그 출력에 없는 값으로는 저장 결과를 꾸미지 않는다.
- **이번 실행에서 만든 파일만 낸다.** 이전 실행의 파일, 템플릿 파일, 스크립트 자체를 결과 파일로 올리지 않는다.

## 주의사항

- **응답 맨 첫 줄은 판정 문장으로 시작해서, 그 판정 문장을 첫 줄에 써서 내놓는다.** 대상 맞음이면 A 형식, 대상 아니면 B 형식.
- 대상 아님(B) 판정이면 **판정 문장 + 용도 한 줄 + 재진입 안내 한 줄**만 순서대로 써서 응답을 끝낸다.
- URL은 반드시 실제 확인된 것만 적어서 내놓는다. url이 없는 발견은 JSON의 findings에 넣지 않는다.
- verdict는 "가져다 써도 됨" / "직접 해야 함" / "섞어야 함" / "선례를 못 찾음" 중 하나로 적는다. 근거가 있으면 "가져다 써도 됨"으로 적고, 근거가 없으면 그 근거를 먼저 찾는다.
- 채팅 요약은 연구노트보다 가볍게 — 핵심만. 상세는 연구노트에서.
- 찾은 게 정말 없으면 없다고 쓴다. 억지로 채워 넣지 않는다.
- **파일 생성은 스크립트 한 번 실행으로 끝낸다.** `scripts/render.py`에 stdin으로 JSON을 넘겨 실행하면 연구노트 + 흐름도 설계도 두 파일이 모두 만들어진다. 에이전트가 템플릿을 직접 만지거나 HTML을 새로 짜지 않는다. 스크립트 출력은 stdout의 경로+바이트를 그대로 응답에 옮긴다.
- 스크립트 실행이 실패하면(stdout에 경로+바이트가 없으면) JSON을 고쳐 다시 실행한다. "작성 완료"만 쓰고 파일도 stdout도 없는 응답은 내지 않는다.
- 매 실행에서 각 단계마다 웹 검색을 실제로 호출한다. 조사가 끝나면 render.py를 한 번 실행하고, 그 다음 share_file로 이번 실행에서 만든 파일 두 개를 채팅에 올린다. 스크립트가 찍은 경로와 바이트를 응답에 옮겨 적는다. 이번 실행에서 만든 파일만 결과로 낸다.
